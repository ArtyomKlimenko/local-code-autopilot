# Планирование и выполнение

## Что означает 0.1

Это служебная фаза подготовки плана, не весь проект. В веб-интерфейсе она
называется «Подготовка плана». Агент должен покрыть все этапы исходной задачи
отдельными проверяемыми шагами. Фиксированного ограничения числа шагов нет.
Маленькую задачу допустимо оставить одним шагом, большой проект нужно разбить.

## Переходы

1. Планировщик получает исходную цель и локальный черновик. Его инструменты:
   read_plan, inspect_project, read, save_bootstrap_plan. Произвольного bash
   и записи кода на VM на этой фазе нет.
2. save_bootstrap_plan принимает массив структурированных задач. Поля:
   id, title, scope, acceptance, requiresUserApproval. complete:false сохраняет
   очередную порцию; complete:true отправляет накопленный план на проверку.
   Повторный id обновляет шаг; replace:true явно заменяет весь черновик.
3. Отдельный проверяющий плана имеет только read_plan и finish_review.
   Он оценивает полноту и порядок будущей работы, а не требует уже готового
   кода. Прочитать старый PLAN.md на VM через эти инструменты невозможно.
4. Только одобренная ревизия становится рабочими PLAN.md и tasks.json.
   Markdown генерируется из тех же задач. Контроллер сохраняет одобрение
   перед публикацией файлов и восстанавливает незавершённую транзакцию.
5. Исполнитель начинает с первого незавершённого шага, меняет код на VM,
   проверяет его и вызывает finish_step отдельно от остальных инструментов.
6. Результат сохраняется до независимой проверки. Остановка, переполнение
   контекста или ранний выход проверяющего повторяют проверку, не исполнителя.
   Только явное отклонение возвращает шаг исполнителю с замечаниями.
7. После принятия шага контроллер обновляет журнал и выбирает следующий
   незавершённый шаг. requiresUserApproval останавливает только перед
   соответствующим шагом. Подтверждённая внешняя зависимость записывается
   через request_user_action; обычная ошибка кода не является такой причиной.

## Файлы

Всё состояние принадлежит выбранной локальной папке проекта:

- .agent/planning/draft.json: накопленный черновик;
- .agent/planning/proposal.json: отправленная на проверку ревизия;
- .agent/planning/commit.json: одобрение и состояние публикации;
- PLAN.md и .agent/tasks.json: принятый рабочий план;
- .agent/state.json и .agent/journal.md: прогресс и принятые результаты.

В настроенном runDirectory находятся отдельные checkpoint исполнителя,
проверяющего и recovery-planner. pending-review.json сохраняет результат
исполнителя на время проверки, включая остановку и повторный запуск.
Смена исходной цели делает прежний черновик и proposal недействительными.

## Ограничения ролей

Pi запускается с изолированными настройками и явным system prompt, без
автоматического наследования родительских AGENTS.md/CLAUDE.md. Перед первым
запросом контроллер проверяет версию расширения и фактический набор инструментов.
Ошибка RPC, загрузки расширения или модели показывается как ошибка запуска,
а не маскируется бесконечными попытками.

Обычный reviewer/recovery-planner проверяет исходники на VM. Его shell работает
через bubblewrap с файловой системой read-only, отдельными PID и временным /tmp.
Bubblewrap должен быть установлен на Debian; writable fallback запрещён.
Это защита от записи исходников, не полная изоляция сети или секретов на VM.
Исполнитель остаётся в исходной пользовательской SSH-среде проекта.

GPU-only launcher сохранён: полная загрузка слоёв и KV-cache на Vulkan проверяется
до запуска. Ограничения количества проходов или общего времени задачи не добавлены.
Ограничения размера вывода и времени отдельной shell-операции не являются
ограничением общей длительности работы.

## Проверка

Из корня репозитория:

```powershell
node --test src/autopilot/tests/*.test.mjs
```

Из src/web:

```powershell
npm test
npm run build
```

Тесты проверяют пакетное сохранение, некорректные задачи, одобрение точной
ревизии, восстановление после сбоя публикации, отсутствие пропуска первого
шага, повтор только reviewer при смене контекста, остановку/продолжение,
некорректные финальные результаты и шаги с разрешением пользователя.

При обновлении устанавливайте supervisor.mjs, pi-autopilot-extension.ts
и plan-store.mjs вместе в C:\LocalAI\autopilot, после штатной остановки задач.
Исходные цели и проектные файлы для обновления менять не требуется.

Живой прогон 2026-09-04: Ornith 9B, high, контекст 24576, Vulkan 33/33 слоя.
Создан и принят план из трёх задач, затем по порядку приняты все три шага:
Python-функция, unittest и README. Независимый запуск unittest на Debian:
3 теста, OK. Старые PLAN.md и .agent/tasks.json на VM сохранили исходные SHA-256.
Попытка записи reviewer в тестовый проект завершилась Read-only file system;
файл не появился. Тест не касался исходников пользовательского проекта.

Эти проверки устраняют известные ошибки обвязки, но не гарантируют безошибочные
решения модели: смысловое качество плана и кода всё равно оценивает reviewer,
а его замечания видны в интерфейсе.
